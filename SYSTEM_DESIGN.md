# System Design — Enterprise Intake Decision Engine

This document records the design assumptions behind the pipeline and, where an assumption turned out to be wrong, the measurement that caught it and the fix that followed. The architecture itself (data flow, file layout, how to run it) lives in `README.md`; this document is about *why* the decision rules are shaped the way they are, and what the golden-set eval (`eval/`) actually found.

## Core design principle

**LLM reasons, the system decides.** Every enforcement action — priority, guardrail routing, whether to proceed or ask for clarification — is deterministic TypeScript reading structured signals the LLM extracted. The LLM is a sensor, not a security boundary. This document is largely a record of what happens when that sensor is imperfectly calibrated, and how deterministic code exposed and corrected it.

## Assumptions

Each assumption below is stated as it was originally held, with its current status and, where it changed, the measurement that forced the change. Numbers come from `eval/results/latest.md`, regenerated by `npm run eval` against the 36-case golden set in `eval/golden-set.ts` — git history preserves the full progression.

### 1. Structured signal extraction is a reliable enough sensor for deterministic gating

**Status:** validated. Priority accuracy on the extreme tiers (P0/P3, the cases with the least ambiguity) has been 100% in every eval run since the golden set was introduced. The deterministic rule table (`config/policy.ts` → `lib/priorityRules.ts`) has never itself produced an incorrect priority given correct signals — every priority miss traced back to signal extraction, never to the rule table.

### 2. A small, config-driven team registry is sufficient without a dynamic or learned classifier

**Status:** validated. `config/teams.json`'s 8 teams + 2 special queues, combined with runtime validation against the registry (`isValidTeam`), has produced a 100% registry validity rate in every eval run — zero hallucinated team names, even when the model picks a wrong-but-real team.

### 3. A fixed "≥2 missing items ⇒ low confidence, ask for clarification" threshold cleanly separates requests safe to route from those that need more information

**Status:** wrong in its initial form.

**Measured:** the baseline eval run (36 cases) showed a **59.3% over-clarification rate** — 16 of 27 cases that should have proceeded straight to routing instead stalled asking clarifying questions. Step 1 was treating "detail that would help resolve the issue" and "detail required to triage the issue" as the same bar, so ordinary, fully actionable requests ("laptop died, board presentation at 9am, I'm the VP of Sales") routinely generated 3–6 "missing" items — asking for device models, OS versions, exact timestamps.

**Revision:** the threshold was not the defect; the signal feeding it was. The `missing_information` prompt guidance was rewritten to explicitly anchor it to a **routing bar, not a resolution bar** — "if you can name a plausible owning team and a plausible urgency from what is written, missing_information should be empty." That single change dropped over-clarification to 11.1% in the same eval, and to 7.4% after later refinements, **without touching the `>=2` threshold at all**. Changing the threshold would have masked a bad signal and needed re-tuning every time a new signal was added; fixing the signal fixed the outcome and stayed correct as other signals changed around it.

### 4. Sensitive-category signals (`hr_sensitive`, `legal_compliance_related`) can be treated identically as "force human review" triggers

**Status:** wrong.

**Measured:** the baseline run showed a **25% sensitive-guardrail false-positive rate** — 8 of 32 non-sensitive-category cases were incorrectly force-routed to Sensitive Intake Review. Nearly every security incident has *some* downstream privacy or compliance dimension, so `legal_compliance_related` fired on a phishing report, an account-compromise report, an auditor-wifi logistics request, and a failed batch job. The serious instance of this: **an in-progress security incident was being routed to a human-review queue instead of to the Security team** — the eval caught this specifically because `misroute-phish-check` and `p0-phishing` both asserted `route: "Security"`.

**Revision:** `hr_sensitive` and `legal_compliance_related` are different *kinds* of signal, not interchangeable severity flags. `hr_sensitive` describes what a request **is about**; `legal_compliance_related` is often a downstream **property** of an operational problem, not its subject. Two changes followed: (a) the prompt was tightened to test "is the requester asking for legal/compliance judgment, or reporting an operational problem?"; (b) a deterministic precedence rule was added in `lib/guardrails.ts` — incident response (`security_incident` / `production_outage`) takes precedence over compliance routing, with the suppression itself recorded in the evidence audit trail rather than silently applied. `hr_sensitive` is deliberately **not** exempt from forcing review — HR matters are never incident response. False-positive rate dropped to 0% in the same eval; the precedence rule is covered by 4 dedicated unit tests in `tests/guardrails.test.ts`.

### 5. A single sequential Claude pipeline (no agent framework, no multi-model orchestration) is sufficient

**Status:** validated for the demo scope. The model-chain fallback (below) extends resilience within this constraint rather than abandoning it — same provider, same credential, still strictly sequential, no parallel branches.

## Versions

### v1 (this build)

- 3-step sequential pipeline (`lib/pipeline/`); deterministic priority, guardrail, and confidence-gate rules extracted to `config/policy.ts` as a small declarative condition tree, evaluated by `lib/policyEval.ts` (no `eval()`, no dynamic code; unknown signal names fail loudly at module load).
- Golden-set eval harness: 36 hand-labeled cases, 12 aggregate metrics, per-category breakdown, full failure detail with extracted signals (`eval/`).
- Consistency harness for run-to-run signal stability (`eval/consistency.ts`).
- Two-view UI: operator (full trace) and requester (explicit allow-list projection, `lib/requesterView.ts`) behind a tab toggle, not separate routes.
- Claude model-chain fallback (`lib/anthropic.ts`): same provider, same credential; advances only on model-specific failures (529/503/404, backed-off 429); never advances on a validation failure, because that would mask a real prompt/schema defect behind a probabilistic workaround; confidence degrades when it fires.
- Minimal in-process duplicate detection (`lib/dedup.ts`): exact-match key (`affected_system:symptom_class`), in-memory `Map`, 30-minute window, report-only `corroborating_reports` count — explicitly **not** wired into priority in this version, and P0 never auto-merges.

### v2 (proposed, not built)

- **Typed `missing_information`**: replace the current free-text `string[]` with a small closed taxonomy (e.g. `{ category: "identifier" | "scope" | "timeline" | "reproduction"; description: string }`), so the confidence gate and eval scoring can reason about *what kind* of information is missing, not just how many items — letting "1 missing identifier" and "1 missing scope description" be weighted differently instead of both counting as exactly one generic item.
- **Fuller deduplication**: wire `corroborating_reports` into priority/routing decisions (with the P0-never-auto-merges guardrail retained as a hard rule, not a convention), and move off a single-process `Map` if this ever needs to run across multiple server instances.
- **Cross-request context resolution**: today every request is independent; `fallback-incoherent` ("the thing from before, you know the one") always degrades to clarification because there is no ticket-reference memory. A real system would need to resolve `INC-####`-style references against a real store, not just note them in evidence when they happen to be given.
